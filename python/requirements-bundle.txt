# What the bundled Python carries, pinned.
#
# Every version here is one this project has measured against, and **every line carries one** —
# an unpinned line in a file whose whole argument is pinning is a hole with a promise over it.
# Loosening one is a decision to be recorded rather than a convenience: a resolver picking something
# newer at package time would ship a stack nobody scored.
#
# **What "measured against" means differs by line, and the difference is worth stating.** The
# execution-provider arms of 2026-08-21 ran on exactly these versions. The translator's
# 8,149-sentence gate of 2026-08-20 did **not**: it ran on `onnxruntime` 1.29.0, on the CPU, as its
# own `translation-quality.json` records under `producedBy`. What carried across unchanged from it
# are CPython 3.12.10 and the three packages that decide the decode — torch 2.13.0,
# transformers 4.57.6, optimum 2.1.0. The runtime did not, and **the gap that leaves is measured
# rather than assumed**: on 2026-08-21 `scripts/measure-translation-agreement.ps1` put the whole
# gate corpus back through these versions and got **8,149 of 8,149 recorded hypotheses back
# character for character**, all 24 languages at 100%, on WebGPU against the gate's CPU.
#
# The CPython 3.14 stack in `tests/fixtures/translation/marian-tokenizer.json` is a different
# artefact's — the tokenizer fixture and the export, not the gate — and this comment claimed it as
# the gate's until 2026-08-21.
#
# **onnxruntime-webgpu, not onnxruntime.** It carries the CPU provider as well, so this one wheel is
# both shipping providers. Measured 2026-08-21 on AMI test, WebGPU scores 16.3319% against the CPU's
# 16.3324% — a difference of 0.0005 points — which is what makes it selectable automatically; CUDA
# is faster and moves the number, and would cost about 1.65 GB of CUDA and cuDNN libraries besides.
#
# **1.27.0 rather than the 1.29.0 this repository pins for .NET**, because that is the newest release
# `onnxruntime-webgpu` is published at. The version costs nothing here: measured 2026-08-21, the
# diariser's parity fixture on cpu@1.27.0 against cpu@1.29.0 is 0.000e+00 — bit-identical.
onnxruntime-webgpu==1.27.0

# **torch is the CPU build and stays the CPU build.** It is here because `transformers.generate`
# needs it and because the diariser calls NVIDIA's own SortformerModules, which is torch code; no
# graph runs on it. That also means IO binding is off in the translator — `optimum` binds a KV cache
# to a torch device — and the published 0.459 s/sentence WebGPU figure is a binding-off figure, so
# it is a floor rather than a ceiling.
#
# On Windows the default PyPI wheel is the CPU build. On Linux it is not, and a bundle built there
# would silently pull about 2 GB of CUDA libraries, so the index is named rather than assumed.
--extra-index-url https://download.pytorch.org/whl/cpu
torch==2.13.0

# The translator: HuggingFace's own tokenizer and beam search over optimum's ONNX Runtime sessions.
# transformers is pinned to the version the checkpoint was exported by — its `generation_config.json`
# records `"transformers_version": "4.57.6"` — because the decode's inherited defaults (length
# penalty 1.0, early stopping off) are that version's.
transformers==4.57.6
optimum==2.1.0
# The distribution that actually ships `ORTModelForSeq2SeqLM` and the merged KV-cache plumbing.
# `optimum==2.1.0` does not pin it: `optimum/onnxruntime/modeling_seq2seq.py` appears in this
# package's RECORD and not in optimum's, so leaving it loose left the decode itself unpinned.
optimum-onnx==0.1.0
sentencepiece==0.2.2

# The diariser: soundfile reads the 16 kHz mono WAV the host writes, and librosa is used for exactly
# one call, `librosa.filters.mel`, which builds the mel filterbank matrix.
#
# **That one call costs about 330 MB**, measured 2026-08-21: it drags in numba, llvmlite, scipy,
# scikit-learn, soxr and pooch. It is here anyway because `diariser/feats.py` is the spike's file
# carried across byte for byte, and that fidelity is what makes the 16.3324% figure describe this
# code. Replacing the call with a committed filterbank would be a different artefact needing its own
# measurement; docs/UNPROVEN.md records it as an open question rather than an oversight.
librosa==1.0.0
soundfile==0.14.0
numpy==2.5.2

# The second diariser (DiariZen), added 2026-08-26. **About 242 MiB of site-packages**, measured as
# the set this stack adds over the one above rather than as a venv total — comparing venv totals
# conflates two different torch builds and overstates it by more than double.
#
# **Two of its packages are not here, and cannot be.** `diarizen` is not published on PyPI at all,
# and its `pyannote-audio` is a genuine fork — 3,996 changed lines across 45 of upstream 3.1.1's 82
# files — so the released wheel is not a substitute. `bundle-python.ps1` installs `--only-binary=:all:`
# on purpose, so neither can be a line in this file. They are vendored instead, under
# `python/uindosill_engines/_vendor/`, exactly as NVIDIA's Sortformer modules already are, and they
# travel because the bundler copies `uindosill_engines` wholesale.
#
# **Nothing below moves numpy or torch, and that was checked rather than hoped.** pyannote-audio
# 3.1.1 predates the numpy 2 ABI break and upstream's own `constraints.txt` pins numpy 1.26.4 and
# torch 2.1.1. Installed against the pins above instead — numpy 2.5.2, torch 2.13.0 — it resolves,
# and with the three compatibility shims in `diariser/diarizen.py` it produces **turn-for-turn
# identical labels** to the stack upstream specifies: 19 turns, 3 speakers, same clip. Had it not,
# the translator's 8,149-sentence gate and the diariser's 16.3324% would have been the price.
#
# **speechbrain is deliberately NOT here, and that is a decision rather than an omission.**
# pyannote imports it inside a `try/except ImportError` for a speechbrain-hosted embedder this
# project does not use -- it uses the pyannote one -- so its absence costs nothing and sets
# `SPEECHBRAIN_IS_AVAILABLE = False`, which is the path upstream wrote for exactly this case.
#
# **Every version of it is unusable here, and the two failure modes are different.** 0.5.16 and
# 1.0.3 raise `AttributeError` at import from `check_torchaudio_backend`, calling
# `torchaudio.set_audio_backend` and `list_audio_backends` -- both removed in torchaudio 2.11 --
# and an AttributeError is not an ImportError, so pyannote's guard does not catch it (gotcha 36).
# 1.1.0 dropped that check and imports cleanly in a virtualenv, which is why it was pinned here
# first. **Measured 2026-08-26 against the assembled bundle, it fails there instead**: importing
# `pytorch_lightning` walks `sys.modules` through `inspect`, meets speechbrain's lazy-module
# machinery -- `__getattr__` -> `ensure_module` -> `getframeinfo` -> `getsourcefile` ->
# `getmodule` -> `__getattr__` -- and recurses until the stack ends. DiariZen cannot load at all.
# It does not reproduce in a virtualenv; it needs the bundle's `._pth` import configuration, which
# is why the bundle had to be assembled and driven before this was visible.
#
# Removing it was checked, not assumed: with speechbrain absent the engine loads from the bundle
# and returns the reference labels for the clip -- 19 turns, 3 speakers.

# torchaudio must match torch 2.13.0 above; 2.11.0 is what that pairs with, and it is pinned like
# everything else here rather than left to the resolver. It is reached only through the shims in
# `diariser/diarizen.py` — its `load` delegates to a TorchCodec this bundle does not carry.
torchaudio==2.11.0

# The speaker embedder's ONNX export, added 2026-08-26. `diariser/embedding_onnx.py` derives a graph
# from the wespeaker checkpoint the catalogue downloads, and `torch.onnx.export(dynamo=True)` is
# built on onnxscript.
#
# **Without it, `--speaker-backend webgpu` fails the load outright** — a named provider is never
# fallen back from, so the missing import surfaces as a refusal naming onnxscript rather than as a
# silent downgrade. The default is unaffected: `auto` resolves to torch and never attempts an
# export, so a bundle missing these two would diarise correctly and only refuse the fast path. An
# earlier version of this comment had it the other way round and described a silent fallback that
# does not exist.
#
# **Derived here rather than downloaded, which is what puts an exporter in a shipping bundle.**
# pyannote publishes a `speaker-embedding.onnx`, but its loader computes a different function —
# it binarises the speaker mask and drops the weighted pooling entirely — so it does not reproduce
# the figures this project publishes. Exporting from the pinned checkpoint keeps one artefact with
# one digest instead of redistributing a second copy of a CC BY 4.0 model.
#
# `onnx` was already here transitively, through optimum-onnx. It is pinned now because this stack
# imports it directly, and an unpinned line in this file is the hole its header warns about.
onnx==1.22.0
onnxscript==0.7.1
